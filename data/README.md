# Synthetic Telco Churn Dataset — Portfolio Edition

## Purpose

This dataset is a leakage-aware, fully synthetic reconstruction inspired by the structure and
aggregate patterns of IBM's fictional Telco Customer Churn sample. It is intended for a public
Data Science / Machine Learning portfolio and contains no original customer rows.

Reference:
https://www.ibm.com/docs/en/cognos-analytics/12.0.x?topic=samples-telco-customer-churn

IBM Community description:
https://community.ibm.com/community/user/blogs/steven-macko/2019/07/11/telco-customer-churn-1113

## Why a synthetic reconstruction?

The academic source project used the IBM sample but mixed predictive variables with fields that
are known only at or after churn, or are generated by another churn model. For the public version,
the data contract intentionally excludes:

- Customer Status
- Churn Score
- Churn Category
- Churn Reason
- geographic identifiers such as City, Zip Code, latitude and longitude
- CLTV as a baseline predictor

These exclusions reduce target leakage, licensing ambiguity, unnecessary memorization risk, and
feature redundancy.

## Target definition

`Churn Next 30D` equals 1 when a customer churns during the 30 days after the `Snapshot Date`.

All predictive variables represent information available at the snapshot.

`Preperiod Satisfaction Score` is explicitly defined as a satisfaction measurement collected
before the prediction window. This timing clarification is deliberate: the source sample describes
Satisfaction Score but does not establish a prediction-time data contract suitable for a leakage
audit.

## Temporal split

The files are not random partitions:

- train: January-June 2025
- validation: July-August 2025
- test: September-October 2025

This creates a simple out-of-time evaluation design.

The total row count remains 7,043 to preserve comparability with the academic source project:

- train: 4,225
- validation: 1,409
- test: 1,409

There are no repeated Customer IDs across splits.

## Synthetic data generation

The generator uses only pre-outcome variables. The target is sampled from a latent logistic risk
function with moderate nonlinear interactions and unobserved noise. The goal is not to create an
artificially easy benchmark. A good project should therefore compare a baseline, an interpretable
logistic model, and at least one nonlinear model, then evaluate whether added complexity produces
a meaningful improvement.

The generated data intentionally includes mild temporal drift in service mix, pricing and churn
prevalence.

## Feature engineering rule

Do not store a manually maintained `N_Servicios` field in the raw data.

If a service-count feature is needed, derive it in code from the agreed service columns and test the
function. `Paperless Billing` is a billing preference and must not be counted as a contracted service.

## Recommended evaluation

Use train for fitting and cross-validation, validation for model/threshold selection, and test once
for final locked evaluation.

Recommended metrics:

- ROC-AUC
- PR-AUC
- Precision / Recall / F1
- confusion matrix
- Brier score
- calibration curve
- lift / gain
- top-k recall
- cost-sensitive threshold analysis

Do not describe associations as causal effects.
